# CAPTCHAMind

CAPTCHAMind is a multimodal Android testing framework for detecting, recognizing, solving, and verifying CAPTCHA interactions in mobile applications.

The project combines Android GUI hierarchy information, screenshots, OCR, structural and spatial context, and optional multimodal large language model reasoning to generate executable interactions such as taps, drags, and ordered selections.

The repository also provides an executor for a direct screenshot baseline. In this condition, a screenshot is submitted to a web-based multimodal LLM without revealing the CAPTCHA type, and the generated ADB commands are copied to the executor for validation and execution.

## Overview

```text
Android device
      │
      ├── UIAutomator hierarchy
      └── Screenshot
              │
              ▼
      GUI information acquisition
              │
              ├── OCR and textual semantics
              ├── structural/spatial context
              └── global interface context
              │
              ▼
      CAPTCHA detection and type recognition
              │
              ▼
      Type-specific action generation
              │
              ▼
      Android action execution and verification
```

The current implementation supports the following CAPTCHA categories:

- text-selection CAPTCHA;
- slider CAPTCHA;
- image-rotation CAPTCHA;
- image-selection CAPTCHA;
- reCAPTCHA-style image selection.

## Source code

| File | Description |
| --- | --- |
| `captchamind.py` | GUI acquisition, OCR, CAPTCHA detection, type recognition, solving, execution, and feedback verification |
| `run_phone_test.py` | Runtime entry point for the CAPTCHAMind pipeline |
| `shiyan.py` | Safe executor for ADB commands generated by a web-based LLM |

## Installation

### Requirements

- Python 3.7 or later;
- Android SDK Platform Tools;
- Android emulator or physical Android device;
- `uiautomator2`;
- `Pillow`;
- `opencv-python` and `numpy`;
- `pytesseract` and a local Tesseract installation for local OCR;
- `requests` for Baidu OCR;
- `zhipuai` for the optional multimodal model backend.

Install the Python dependencies with:

```bash
pip install uiautomator2 xmltodict Pillow opencv-python numpy pytesseract requests zhipuai
```

Verify that ADB can find the device:

```bash
adb devices
```

The device must be listed with the status `device` rather than `offline` or `unauthorized`.

## Configuration

API keys must be provided through environment variables. Do not commit API keys to the repository or include them in experiment logs.

```powershell
$env:ZHIPUAI_API_KEY = "<your-key>"
$env:BAIDU_OCR_API_KEY = "<your-key>"
$env:BAIDU_OCR_SECRET_KEY = "<your-secret>"
```

Before publishing the artifact, make sure that no credential is embedded in `captchamind.py` or any other source file.

## Quick start: CAPTCHAMind pipeline

Start the target application and place the device on the CAPTCHA page. Run the ADB backend with:

```powershell
python run_phone_test.py `
  --backend adb `
  --serial emulator-5554 `
  --save-root .\runtime_output
```

The command performs GUI information acquisition and prints:

- the captured screenshot and UI hierarchy paths;
- CAPTCHA detection results;
- recognized CAPTCHA type and confidence;
- the generated solving plan;
- the verification prompt and structured context.

To execute the generated actions on the device, add:

```text
--execute
```

The UIAutomator2 backend can be selected with:

```powershell
python run_phone_test.py `
  --backend uiautomator2 `
  --serial emulator-5554 `
  --save-root .\runtime_output
```

The ADB backend can be used when the phone-side UIAutomator2 service is unavailable.

## Direct screenshot comparison condition

`shiyan.py` implements the execution part of the direct screenshot baseline. The LLM interaction itself is performed through a web interface.

1. Start the target application on the CAPTCHA page.
2. Run the executor:

```powershell
python shiyan.py `
  --serial emulator-5554 `
  --paste
```

3. Upload the pre-execution screenshot to the web-based multimodal LLM.
4. Do not provide the CAPTCHA type to the LLM.
5. Copy the generated ADB commands into the executor.
6. Enter `END` on a separate line.

Example input:

```text
adb shell input tap 500 800
adb shell input swipe 200 900 800 900 600
adb shell input keyevent KEYCODE_ENTER
END
```

The executor accepts the following command classes:

```text
adb shell input tap X Y
adb shell input swipe X1 Y1 X2 Y2 [DURATION_MS]
adb shell input keyevent KEYCODE_...
adb shell input text TEXT
adb shell sleep SECONDS
sleep SECONDS
```

Command chaining, pipes, redirection, unsupported ADB subcommands, invalid coordinates, and unsupported key codes are rejected. Commands are executed without `shell=True`.

## Experimental protocol

For each application and CAPTCHA instance:

1. reset the application to the same initial state;
2. capture and preserve the input screenshot;
3. use the fixed prompt template and model configuration;
4. record the model name and prompt version;
5. execute the generated action sequence without manual coordinate correction;
6. determine success using the predefined verification criterion;
7. preserve the command sequence, execution log, and result label.

For the direct screenshot condition, the CAPTCHA type is used only as a post-hoc ground-truth label. It is not provided to the model before action generation.

## Evaluation metrics

The artifact supports the following evaluation metrics:

- **CAPTCHA detection accuracy**: whether the interface contains a CAPTCHA;
- **type-recognition accuracy**: whether the predicted CAPTCHA category matches the ground truth;
- **solving success rate**: whether the CAPTCHA is successfully completed;
- **average solving time**: time from action execution to outcome determination;
- **first-success attempt**: the first successful solving attempt;
- **failure-category distribution**: recognition, localization, execution, or application-response failure.

The same initial state, number of trials, success criterion, and annotation procedure should be used for all compared methods.

## Output organization

Each trial should be stored separately:

```text
results/
  <application>/
    trial_01/
      before.png
      hierarchy.xml
      prompt.txt
      commands.txt
      execution.log
      result.json
```

Example `result.json`:

```json
{
  "application": "<application-name>",
  "trial": 1,
  "captcha_type": "<ground-truth-type>",
  "model": "<model-name>",
  "backend": "adb",
  "recognized_type": "<predicted-type>",
  "success": true,
  "failure_category": null
}
```

For reproducibility, also record the Android version, emulator image, screen resolution, application version, device serial, Python version, dependency versions, OCR provider, model configuration, and prompt version.

## Scope

The released implementation covers single-page CAPTCHA acquisition, recognition, solving, action execution, and verification.

Application-wide exploration, event deduplication, UTG construction, and coverage computation should be released together with the corresponding exploration and statistics modules when those results are reported in the paper.
